# AGENTS.md

## Commands

- Use `pnpm`; this is a single-package workspace (`pnpm-workspace.yaml` includes only `.`). There is no test runner or CI workflow.
- `pnpm dev` runs Vite on port 3000; `pnpm preview` builds first and serves on 4173.
- Verification: `pnpm lint`, `pnpm typecheck`, `pnpm build`. `pnpm check` is Prettier-only over `src/**/*.{ts,tsx}` and currently fails: `.prettierrc` enforces double quotes/semicolons while existing source (including generated `routeTree.gen.ts`) uses single quotes/no semicolons.
- Avoid blanket `pnpm format` unless reformatting all of `src` is intended; it runs `prettier --write` over `src/**/*.{ts,tsx}` (including generated files) then `eslint --fix`.
- Cloudflare types: `pnpm cf-typegen` regenerates tracked `worker-configuration.d.ts`. `pnpm deploy` builds, then `wrangler deploy`.

## App structure

- TanStack Start file routes: `src/routes/__root.tsx` owns the HTML shell/head; `src/router.tsx` creates the router; `src/routeTree.gen.ts` is generated by Vite/TanStack Router (`pnpm generate-routes` is just `vite build`) — never hand-edit. ESLint ignores it; Prettier does not.
- Use `#/...` for `src` imports (`package.json` `imports` + tsconfig `paths`). `@/...` is not configured, despite `.prettierrc` importOrder mentioning it.
- Tailwind v4 entry is `src/styles.css`, imported as `?url` by `__root.tsx` (`.vscode/settings.json` points to a nonexistent `src/globals.css`).

## Cloudflare / deploy

- `@cloudflare/vite-plugin` runs SSR in the Worker environment; local state is gitignored `.wrangler/`. After build, Wrangler is redirected from root `wrangler.jsonc` to generated `dist/server/wrangler.json` via `.wrangler/deploy/config.json` — don't edit generated config.
- `wrangler.jsonc` uses `nodejs_compat`; runtime types in `worker-configuration.d.ts` are tracked and eslint-ignored.

## Git hooks

- Pre-commit: lint-staged runs `prettier --write` + `eslint --max-warnings 0` on staged `src/**/*.{ts,tsx}`, and Prettier on staged `*.md`.
- Commit-msg: conventional commits, types include `release` and `wip`; lowercase type, header ≤100, no trailing period.
- Post-commit/post-checkout launch a detached graphify rebuild; `GRAPHIFY_SKIP_HOOK=1` suppresses it.

## graphify

This project has a knowledge graph at graphify-out/ with god nodes, community structure, and cross-file relationships.

When the user types `/graphify`, use the installed graphify skill or instructions before doing anything else.

Rules:

- When graphify-out/graph.json exists, run `graphify query "<question>"` before your first grep, search or source-file read for a codebase question, and put this rule in every subagent prompt that explores code. Read raw files only for lines the graph or an earlier read already located. Use `graphify path "<A>" "<B>"` for relationships and `graphify explain "<concept>"` for focused concepts. These return a scoped subgraph, usually much smaller than GRAPH_REPORT.md or raw grep output.
- Dirty graphify-out/ files are expected after hooks or incremental updates; dirty graph files are not a reason to skip graphify. Only skip graphify if the task is about stale or incorrect graph output, or the user explicitly says not to use it.
- If graphify-out/wiki/index.md exists, use it for broad navigation instead of raw source browsing.
- Read graphify-out/GRAPH_REPORT.md only for broad architecture review or when query/path/explain do not surface enough context.
- After modifying code, run `graphify update .` to keep the graph current (AST-only, no API cost).
- A committed graphify-out/graph.json is rewritten whole on every build, so a large diff to it in a pull request is expected. Do not flag it as churn or suggest skipping the graph rebuild or its hooks.
